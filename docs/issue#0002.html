Design Decisions

Decision Keep conflict semantics in the shared contract

Ambiguity: The original Issue and acceptance matrix used a generic revision code, while the detailed API contract used a Project-specific code.

Choice: Following the user's decision, the contract now exposes PROJECT_REVISION_CONFLICT with validated currentRevision details.

Rationale: Frontend and Server consumers receive the same stable domain meaning and can implement a recoverable refresh flow.

Decision Keep protocol schemas runtime-neutral

Choice: Zod schemas and constants live in the contracts workspace; Hono-specific status and error construction remain in the Server.

Rationale: The browser can validate envelopes without importing Node, Hono, filesystem, or database implementations.

Tradeoffs

Tradeoff Domain-specific code over a generic revision code

Alternatives: A generic code is reusable across entities; a Project-specific code matches the published API and gives consumers precise behavior.

Choice: Use the domain-specific code and reject the old generic literal in its specialized schema.

Why: This avoids ambiguity now without prematurely defining conflict contracts for domains that do not yet expose revision APIs.
