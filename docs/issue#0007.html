Implementation Notes

Issue #0007 — Project lifecycle vertical slice — 2026-08-09

Design Decisions

Decision Keep Project state derived and contract-first

Choice: Shared schemas define create, patch, archive, list, response, and Overview shapes; stage and pipeline are computed by ProjectService.

Rationale: Client and server validate one contract while projects remain free of writable stage or progress columns.

Decision Make create replay-safe in one transaction

Choice: ProjectRepository writes the Project and its workspace-scoped idempotency result in one SQLite transaction.

Rationale: Interrupted or repeated submissions return the original Project without leaving a committed partial record.

Decision Separate domain state from form state

Choice: Zustand stores Project collections and Overview data; title, brief, content type, status, platform, and duration remain local to ProjectForm.

Rationale: Cross-route Project data is reusable without turning temporary input into global state.

Deviations

None — all six API endpoints and the specified Project-only UI flows are implemented without adding later Asset or Task workflows.

Tradeoffs

Tradeoff Opaque tuple cursor over offset pagination

Alternatives: Expose updatedAt directly, or use numeric offsets.

Choice: Encode the descending (updatedAt, id) tuple as a base64url cursor.

Why: Equal timestamps remain deterministic and list changes do not create offset gaps.

Tradeoff Minimal Foundation pipeline

Alternatives: Predefine every future creation stage, or expose only the current Project.

Choice: Overview computes the SPEC-backed idea and script stages and leaves later domain stages to their owning Issues.

Why: The Overview is useful now without pre-implementing P1 workflows.

Open Questions

None — all FND-007 acceptance criteria have contract, integration, component, production-build, and Chromium E2E evidence.
