Issue #0006 — Routing and planned-module placeholders — 2026-08-09

Design Decisions

Decision Keep routes declarative and data-free

Choice: Route modules compose static Foundation states and links; no Project, Asset, Task, or Settings data stores were introduced.

Rationale: FND-006 proves navigation and recovery contracts without coupling to later lifecycle APIs.

Decision Treat unavailable capability as an explicit product state

Choice: Every placeholder names the module, delivery phase, short scope statement, and a valid return route.

Rationale: Planned work remains discoverable without presenting fabricated results or dead ends.

Decision Make the mobile sidebar a keyboard-contained interaction

Choice: Opening moves focus inside; Tab wraps at both ends; Escape closes from anywhere; closing restores the menu control.

Rationale: The overlay cannot leave keyboard users interacting with obscured page content.

Alternatives: Hide Project Detail until project persistence exists, or expose a route-contract preview.

Why: This makes the complete child navigation testable while respecting the Foundation dependency boundary.
