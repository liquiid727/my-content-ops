Issue #0009 — Persistent Task Runtime and Seed Provider — 2026-08-09

Design Decisions

Decision Registry owns Task input boundaries

Choice: Every Task type registers a handler with an input parser; the Seed handler uses the shared seed schema before persistence and again before execution.

Rationale: Arbitrary JSON never reaches a Provider and unsupported types fail without creating Tasks.

Decision Make state and event one write boundary

Choice: enqueue, claim, transition, and generation completion each update Task state and append the corresponding TaskEvent in one SQLite transaction.

Rationale: REST snapshots and future SSE consumers cannot observe a state without its event.

Decision Keep Provider errors and inputs redacted

Choice: Generation snapshots retain prompt length/hash and capability metadata, while handler failures expose only stable TASK_HANDLER_FAILED text.

Rationale: Provider details and input secrets do not cross the persistence or API boundary.

Deviations

None — retry, SSE, heartbeat, and startup recovery remain explicitly deferred to FND-010.

Tradeoffs

Tradeoff Single-process serial drain

Alternatives: Add configurable concurrency now, or prove persistence and cancellation with one in-process drain.

Choice: Run one task at a time in Foundation.

Why: It keeps claim/cancel semantics deterministic while preserving the handler and provider interfaces needed for later concurrency.

Open Questions

None — all FND-009 criteria have state-machine, failure, transaction, REST, persistence, and build evidence.
