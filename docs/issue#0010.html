Implementation Notes

Issue #0010 — Task SSE, replay, and startup recovery — 2026-08-09

Design Decisions

Decision Durable database IDs are the only stream cursor

Ambiguity: The client needed replay and snapshot calibration without adding browser persistence.

Choice: SSE IDs come directly from task_events.id; the client keeps the cursor only in memory and sends it as Last-Event-ID.

Rationale: SQLite remains authoritative, while duplicate IDs can be rejected before any Zustand mutation.

Decision Reset advances to the latest valid workspace cursor

Ambiguity: A missing or retained-away cursor cannot be replayed safely.

Choice: The server emits stream.reset with the latest valid ID; the client refreshes active Tasks and adopts that cursor.

Rationale: This prevents both stale state and an endless reset loop after reconnection.

Decision Startup recovery follows handler capability

Choice: Recoverable running Tasks return to queued; Tasks without a recoverable handler become terminal failed with a stable redacted code.

Rationale: Restart behavior is explicit per handler and never silently repeats an unsafe operation.

Deviations

None — the implementation follows the Issue and API contract, including 15-second heartbeat, 45-second client watchdog, stream reset, and seven-day event retention.

Tradeoffs

Tradeoff Fetch streaming instead of native EventSource

Alternatives: Native EventSource provides parsing and automatic reconnect, while a fetch reader requires a small parser.

Choice: Fetch streaming was selected so the client can control Last-Event-ID, capped exponential backoff, the 45-second inactivity watchdog, and terminal cancellation.

Tradeoff Poll persisted events on each connection

Alternatives: An in-process publish/subscribe registry is lower latency but loses cross-restart durability and adds subscriber lifecycle state.

Choice: Short SQLite polling keeps replay and live delivery on one durable source; the loop exits and releases its connection bookkeeping when the stream aborts.
