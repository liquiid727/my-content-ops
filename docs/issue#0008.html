Issue #0008 — Asset file storage and Version foundation — 2026-08-09

Design Decisions

Decision Treat storage paths as server-owned capabilities

Choice: Upload names are display-only; storage paths are generated from Asset ULIDs, validated segment-by-segment, and rejected when a directory is a symlink.

Rationale: Neither request fields nor database values can escape the controlled files root.

Decision Compensate across SQLite and the file system

Choice: Write a 0600 temporary file, inspect MIME/signature and hash, insert metadata, atomically rename, and hard-delete only the just-created record if rename fails.

Rationale: SQLite and the file system cannot share a transaction, so every failure path cleans the temporary artifact and restores consistency.

Decision Restore by append-only transaction

Choice: Version restore copies the old snapshot into a new incremented Version while switching the single current marker and storing the idempotency result in one transaction.

Rationale: History is immutable, replay-safe, and protected by the partial unique index.

Deviations

None — thumbnail generation remains null because no thumbnail endpoint exists in API §6; later processing is not fabricated.

Tradeoffs

Tradeoff Foundation buffering over streaming internals

Alternatives: Add a streaming multipart parser and incremental range file streams now, or keep the Hono Foundation path bounded by the 200 MB server limit.

Choice: Buffer the bounded upload/content in this Issue while still persisting through temporary files and supporting HTTP byte ranges.

Why: It satisfies the specified local limit and safety invariants without introducing a second upload stack before larger media requirements exist.

Open Questions

None — all FND-008 criteria have security, integration, database-constraint, UI-state, build, and Chromium E2E evidence.
