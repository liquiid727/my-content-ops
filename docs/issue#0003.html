Issue #0003 — SQLite, Drizzle migrations, and repositories — 2026-08-09

Design Decisions

Decision Treat SQL migrations as immutable history

Ambiguity: Drizzle can generate migrations, but the data contract explicitly requires checksum rejection when applied history changes.

Choice: Execute ordered SQL files through a small SHA-256 migration runner and use Drizzle schema for typed access.

Rationale: Constraints remain reviewable and immutable while repositories retain type-safe query construction.

Decision Keep transaction ownership inside repositories

Choice: Version current switching and Task state/event writes are exposed as single repository operations.

Rationale: Business modules cannot accidentally update half of a required atomic state transition.

Deviations

None — every Foundation table and required storage invariant is represented in the first migration.

Tradeoffs

Tradeoff File-backed temporary databases instead of SQLite memory mode

Alternatives: In-memory tests are faster; isolated temporary files exercise WAL, migration checksums, directory creation, and cleanup.

Choice: Use a fresh mkdtemp directory per test database.

Why: It tests the same persistence behavior used in production and proves that test artifacts are removed.

Open Questions

None — bootstrap identity and default records are intentionally owned by FND-004.
