<!-- Ch03 · 六个经验 -->
<!-- Step 0: 经验一 · 把需求说清楚 -->

第一张保命符：

别让 Agent 猜。

我以前特别喜欢一句话——

"帮我做个登录。"

然后它真的去做了。

做完以后，我和它两个人都沉默了。

因为它理解的登录，和我理解的登录，完全不是一回事。

后来我才明白——

不是它笨。

是我说得太随便了。

现在我会把目录、字段、方案、验收标准，一次讲清楚。

Agent 瞬间就正常了。

---

<!-- Step 1: 经验二 · 上下文要喂够 -->

但光把需求写清楚还不够。

因为 Agent 不知道你项目的背景。

上下文——就是你们的聊天背景——它如果没有，就只能瞎猜。

所以还得把 Spec 文件、agents.md、相关的文件路径，这些材料都塞给它。

Spec 就是需求文档。

agents.md 就是给 Agent 看的项目说明书。

你喂的背景越完整，它干的活越靠谱。

偷懒不喂，后面返工的时间，会十倍还回来的。

真的。

---

<!-- Step 2: 经验三 · 审查，锅是你的 -->

但就算喂了背景，也不能闭眼信任它。

因为这个项目的锅——

是你的。

不是它的。

怎么审？两个动作。

一，看 diff——就是看它改了哪些东西。不用看全部代码，但变了什么，你得知道。

二，亲手跑一下——它说能跑不算，你跑起来才算。



---

<!-- Step 3: 经验四 · Plan 模式先说后做 -->

后来我又学会了一件事。

别急着让它干。

先让它说。

"你准备怎么干？"

Claude Code 有个 Plan 模式，我现在几乎每次都会先开它。

它会告诉我：准备改哪些文件、分几步做、哪些地方需要我确认。

我点头，它再开始干。

听起来像多了一步。

但实际上，少了无数步返工。


还有就是在出方案前

追问它——"你打算怎么做？为什么？还有没有其他方案？"

甚至可以让两个 Agent甚至多个Agent 互相辩论。

效果出奇地好。

---

<!-- Step 4: 经验五 · 翻车了用 rewind -->

即便这样，翻车还是会发生。

因为我偶尔会脑子一热——

需求没说全就让它跑了，还跑了一大截，git 记录也忘做了。

然后一看，这代码已经不是屎山了，是屎山山脉。

这时候不要慌。

Claude Code 有个 rewind 命令，可以帮你回滚到之前的状态。

Codex 没有完全一样的能力，但它们背后有同一个后悔药——

Git。

小步提交，一个功能一个 Commit，大改前先建分支，出现风险立即停。

Git 才是真正的后悔药。

翻车不可怕。

可怕的是翻了车，什么退路都没有。
---

<!-- Step 5: 经验六 · 拆任务换 Agent -->

最后一张保命符——

上下文要主动管，别等 Agent 自己变傻。

上下文，就是你们整个对话的历史记录。

对话太长，它开始答非所问、忘记之前的约定——这些都是信号。

这时候要把任务拆开，把成果交接给新的 Agent 继续，而不是逼着同一个 Agent 硬撑。

以后模型可能会自动处理这些。

但现在，还是得靠我们自己盯着点。

---

<!-- Ch04 · Spec 与 AGENTS.md -->
<!-- Step 0: Spec 到底长什么样 -->

说了很多次"把需求写清楚"，那 Spec 到底要写成什么样子？

本质就三件事。

第一：意图清晰——你到底想解决什么问题？

第二：约束明确——边界在哪，不能碰什么？

第三：验收可测——怎么判断这件事做完了？

说起来简单。

大部分人（包括我）第一次写出来，都是一团浆糊。

这个需要练。

但先写，比不写强。

---

<!-- Step 1: AGENTS.md 是 Agent 的入职手册 -->

除了 Spec，还有一个东西让我省了很多时间——

AGENTS.md。

可以理解为：给 Agent 看的入职手册。

人类读 README，Agent 读 AGENTS.md。

里面写项目是什么、目录怎么分布、代码风格、哪些命令能跑、哪条线不能碰，还有之前踩过什么坑。

写清楚这些，每次开新对话都不用从头解释。

省时间，还能防 Agent 乱来。

初版不用完美，先有就行，边用边补。

---

<!-- Ch05 · 进阶 -->
<!-- Step 0: 上下文管理升级 -->

基础有了，来聊聊更进阶的打法。

第一个坎——上下文管理。

上下文，就是聊天记录的总量。

管不好，Agent 会疯狂犯错、忘记 Spec、响应越来越慢。

更糟的是：当你发现它变傻的时候，它在"犯蠢"期间已经动了很多东西。

解法是阶段交接——

做完一段，让它把成果总结出来，开新对话继续。

干净、无损、可控。

比压着它一直跑，稳多了。

---

<!-- Step 1: MCP · Skill · SubAgent · Workflow -->

上下文管好了，Agent 的能力还能继续扩展，靠四个组件。

MCP——外部能力协议。就是给 Agent 接上外部工具，数据库、API、搜索，统统能用。

Skill——可复用脚本。把反复做的事情定义好，一次写，处处调用。

SubAgent——分身。派出去干活，只把结论带回来，不污染主对话。

Workflow——流水线。把这些串起来，端到端自动执行。

这四个组合起来。

一个人真的可以干很多事。

---

<!-- Step 2: 并行开发 -->

说到一个人干很多事——有个打法我个人特别喜欢。

Spec 加 Git Worktree 加 SubAgent，做并行开发。

Worktree，就是给项目开几个平行世界，互不干扰。

把任务拆开，每个平行世界里启一个 Agent 同时推进，你来回监督，谁做完了先 review 谁。

我当时学会这个打法以后，感觉自己无敌了大概十分钟。

然后现实给了我一巴掌。

所以后面就有了下面这些。

---

<!-- Ch06 · 工程约束 -->
<!-- Step 0: CI/CD + Hooks + Worktree -->

能力越大，越需要安全网。

三根柱子。

CI/CD——机器审查官。代码格式不对、测试没过，别想合进去。它不讲情面，但它救过我无数次。

Hooks——在 Agent 每一步操作前后设卡。就是在它的生命周期里埋检查点，拦住它不该做的事。

Git Worktree——并行开发的隔离保障。多个 Agent 同时跑，互不污染。

AGENTS.md 告诉它应该做什么，Hooks 拦住不该做的，CI 验证做完后对不对——

三层叠加，才睡得着觉。

---

<!-- Step 1: 测试是最后防线 -->

还有一个我以前最容易偷懒的——测试。

Agent 会写一种非常迷惑的代码。

结构正确、命名合理、注释到位。

跑起来是坏的。

看起来很专业，其实里面已经在暗地里算错了。

对抗这个的唯一办法，是测试驱动——

先写测试，定义期望。

让 Agent 写实现。

跑测试，不通过就重来。

这是确保产出质量的最后一道防线。

偷不得。
