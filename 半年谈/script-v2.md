# Vibe Coding 半年谈 · 口播稿 v2

<!-- Ch01 · 开场 -->
<!-- Step 1: Hook -->

这半年，我几乎每天都在和 AI 打交道。

准确一点说——

我几乎每天都在挨 AI 的打。

有一次，下午两点我开始让 Agent 帮我做一个功能。

Agent 开始跑，我端着水杯，心情很不错。

大概过了四十分钟，我打开终端，看了一眼 Git Diff。

一万两千行。

……

我数了三遍。

没错，一万两千行。

不是因为功能有多大。

是因为它把我一半的项目顺手重构了。

它说：「我感觉这样更好。」

我盯着屏幕，很平静。

那种平静，不是接受，是放弃。

---

<!-- Step 2: 半年前 vs 半年后 -->

那段时间，我理解的 Vibe Coding 特别简单。

给 AI 一句话。

然后双手合十。

默念：哥，求你别翻车。

如果结果不错——开心。

如果结果不对——改提示词，继续祈祷。

我那时候以为，这就是 AI 开发的全部。

事后我才知道，那不叫 Vibe Coding。

那叫 Vibe Debug。

现在呢？

现在我有一批 Agent 在帮我干活。

我在发号施令，我在做 Review，我在管进度。

好像带了个团队。

当然，这个团队翻起车来，比我一个人翻车还要壮观。

---

<!-- Step 3: 今天讲什么 -->

所以今天这期，我想讲清楚一整条变化链。

从最开始的对着 AI 许愿——

到给 AI 立规矩、带分工——

再到用工程手段把整个场面兜住。

不是什么特别厉害的方法论。

就是一些，让我少熬几个夜的经验。

如果你也在用 Claude Code、Codex 或者 Cursor——

希望里面有一条，能帮你少踩一个坑。

从一个过来人这里，提前知道这些。

真的，别问我怎么知道的。

---

<!-- Ch02 · 蜕变 -->
<!-- Step 1: AI 工具形态变了 -->

先说一个背景。

半年前大家讨论的 Vibe Coding，和今天讨论的，其实已经不是一回事了。

以前，AI 更多是辅助补全。

我写代码，它帮我填。

而现在，它开始读整个项目、改代码、跑测试、调用工具——

然后给你一千多行的结果。

它现在更像团队里新来的工程师。

执行力很强。

速度很快。

对，说的就是那种执行力强、速度快，但你要没说清楚，他就真的给你「实现了一个功能」的新工程师。

---

<!-- Step 2: 身份变了 -->

所以这半年，我最大的变化，不是写代码更快了。

是身份变了。

以前我是写代码的人。

现在，我更像是在带团队。

Agent 是工程师，我是那个负责设计、决策、Review 的人。

听起来挺帅。

但我刚开始的时候，完全不会带。

Agent 干到一半，我不知道怎么判断它做得对不对。

然后就在旁边「感觉应该没问题」。

那就是我。

---

<!-- Step 3: 为什么总翻车 -->

后来我一直在想，为什么会这样翻。

它明明那么聪明，响应那么快。

后来我发现，很多翻车，不是模型的问题。

是我们没说清楚三件事：

要去哪。

哪些地方不能碰。

做到什么程度才算完成。

这三件事没说清楚，Agent 只能猜。

猜不中，就翻车。

猜中了，是运气。

后来我给自己定了一条原则：

不要让 Agent 猜。

这是我过去半年，最大的收获。

---

<!-- Step 4: 六张保命符预告 -->

从那以后，我把翻过的所有车整理了一遍。

发现它们基本都来自同一个问题：

我在让 Agent 猜。

慢慢总结出了六张保命符。

如果半年前有人告诉我这些，我能少熬很多次。

大概是这样一条链：

先别让 Agent 猜；

然后给它足够的上下文和约束；

再把这些经验沉淀成 Spec 和 AGENTS.md；

开始真正管理上下文、能力和分工；

最后用工程手段把整个场面兜住。

我们从头开始。

---

<!-- Ch03 · 六张保命符 -->
<!-- Step 1: 保命符一 · 别让 Agent 猜 -->

我以前最喜欢跟 Agent 说的一句话——

「帮我做个登录。」

然后它真的做了。

用户能输入名字密码，点提交，成功了。

我很开心，我以为功能做好了。

后来顺手打开代码，看了一眼实现。

密码明文存的。

没有哈希，没有 session，没有权限校验，退出按钮也没有。

我问它：你为什么这样做？

它说：你只说了「做个登录」。

那一刻，我和它两个人都沉默了。

不是它笨。

是我没说清楚。

后来我的习惯就变了——

告诉它要改哪些目录，用什么方案，哪些地方不能动，验收标准是什么。

说清楚的需求和没说清楚的需求，返工量可能差十倍。

Agent 不是读心术大师，它只是执行者。

---

<!-- Step 2: 保命符二 · 上下文要喂够 -->

说清楚需求，只是第一步。

还有一件事同样重要——

你得让它知道背景。

很多人以为 Prompt 很重要，改来改去改提示词。

其实真正重要的是 Context，就是聊天背景。

Agent 不知道你的项目历史。

不知道哪个模块是三年前的祖传代码，动一下会发出奇怪的声音。

不知道团队规范里有哪些雷区。

你丢给它一句需求，它就只能在黑暗里摸索。

所以我现在每次开任务，都会一起给它：Spec、AGENTS.md、目录结构，还有相关文件。

它看完，就像入职了一样。

你给的信息越完整，它越像做了三年的老员工。

你不给，它就是第一天来上班，什么都不知道。

---

<!-- Step 3: 保命符三 · Review 是你的职责 -->

但就算背景喂够了，也不能闭眼信任它。

因为这个项目的锅，是你的。

不是它的。

我给自己定了一条死规矩——

Agent 写什么，可以不逐行看，但 Diff 一定过一遍。

就是它改了哪些东西，哪些文件，加了什么，删了什么。

就这一步，帮我拦住了太多「看起来没问题但其实已经歪了」的结果。

另外，它说能跑，不等于真的能跑。

我一定亲自跑一遍。

还有一个我最近特别喜欢的方法——

直接开两个 Agent，让它们互相 Review 对方的结果。

这两招一起用，你就不是在「相信 AI」，你是在「审查 AI」。

差距很大。

---

<!-- Step 4: 保命符四 · Plan 模式先说后做 -->

前面三张保命符用下来，翻车频率低了很多。

但我后来发现，我一直活在救火的逻辑里。

翻了救，救了继续，再翻再救。

我想能不能换一种方式——

别让它先干，先让它说。

「你准备怎么干？」

Claude Code 有 Plan 模式，就是让它先列计划，你确认了再执行。

我现在每次开大一点的任务，都会先问：

准备改哪些文件？

分几步完成？

最大的风险是什么？

有没有其他方案？

等我看完，觉得没问题，再开始。

这个步骤看起来慢，实际上帮我省掉了最多的返工时间。

真的，就这一步，差距很大。

---

<!-- Step 5: 保命符五 · 翻车不可怕，可怕是回不去 -->

即便做了这些，翻车还是会发生。

我还是翻了很多次。

最长的一次，Agent 连续跑了二十多分钟。

我一直以为在往前走。

然后打开来看——

方向全错了。

那二十多分钟做的东西，全部需要重来。

而且那个会话拉得特别长，状态乱成一团，根本不知道从哪回滚。

那一刻，脑子里只有一句：完了。

从那以后，我重新学了一遍 Git。

小步提交，一个功能完成立刻 Commit 一次，开实验先建分支，感觉不对立刻停。

Agent 在连续改多个文件的时候，你必须让自己随时能停、能看、能退。

不然它一口气吐出来几千行 diff，你不是在 Review——

你是在哭着考古。

可以不相信模型，但一定要相信版本控制。

---

<!-- Step 6: 保命符六 · 主动管理上下文 -->

最后一张保命符——

你得主动管上下文，别等 Agent 自己变傻。

有时候你会发现它开始有点不对。

前面讲过的事，它好像忘了。

刚定好的结论，下一步没有考虑进去。

你说什么，它答的跟你问的有点对不上。

出现这些信号，不要硬撑。

这是在告诉你：上下文已经太重了。

聊天越来越长，就像往一个脑子里不断塞东西，后面越来越混。

这个时候我会做一次阶段交接——

把确认过的结论、改过的文件、没解决的问题，整理成一小段，然后新开一个 Agent，把这段当背景给它。

新的 Agent 一上来，看到的是干净的上下文。

不是你们吵了一个小时之后留下来的感情债。

---

<!-- Ch04 · Spec 与 AGENTS.md -->
<!-- Step 1: Spec 三问 -->

说了这么多「把需求写清楚」——

那具体要写成什么样子？

我第一次尝试写 Spec，写出来的东西是一团浆糊。

很多废话，没有重点，Agent 看完还是不知道要做什么。

后来我发现，一个好的 Spec，其实只要回答三个问题。

第一：我要解决什么？

第二：什么不能碰？

第三：怎样算完成？

就这三个。

你跟 Agent 说「帮我实现一下这个功能」——它理解的是模糊愿望。

你跟它说「这几个用例必须过，那个文件不能改，跑通这条 API 才算完成」——那就是明确边界。

写清楚不容易，要练。

但先有一个，比完全没有强太多。

---

<!-- Step 2: AGENTS.md 入职手册 -->

每次开新会话，我以前都要重新解释一遍项目。

它是做什么的、技术栈是什么、哪些命令常用、哪个目录别乱动。

重复了大概十几次之后，我受不了了。

后来我写了一个 AGENTS.md。

就是项目的「入职手册」，放在根目录，每次 Agent 进来自己就能读。

项目是什么、目录怎么组织、技术栈、常用命令、代码规范、已知坑点——

从那以后，很多重复解释就消失了。

我的建议是——

不要追求一次写完，先有，再不断补充。

它将来会成为整个项目最重要的工程文档之一。

真的，别问我怎么知道的。

---

<!-- Ch05 · Agent Engineering 进阶 -->
<!-- Step 1: 上下文管理 -->

走到这里，你会发现，你开始不只是管单个任务了。

你开始想：怎么让整个项目长期不翻。

这时候，上下文的问题会变得非常明显。

我以前有个习惯——一个 Agent 会话能聊到天荒地老。

聊到后面，它开始出现一种很诡异的状态。

前面说过的话，它好像没记住。

刚刚讨论过的方案，它好像没看见。

这不是模型变笨了。

是上下文炸了。

你往它脑子里塞进去的每一段对话、每一份文件、每一条日志，都是重量。

塞得越多，后面理解新东西的成本越高。

有时候你以为你在补充信息——

实际上你是在往它脑子里塞购物小票。

---

<!-- Step 2: MCP · Skill · SubAgent · Workflow -->

再往后，我开始真正弄明白这四个东西。

MCP——外部能力协议。给 Agent 接上外部工具，数据库、API、搜索都能用。解决的是：Agent 能不能碰到外面的世界。

Skill——可复用操作说明书。告诉它这个场景应该按什么套路来。解决的是：Agent 知不知道怎么稳定做一件事。

SubAgent——分身。派一个去查模块 A，派另一个去查模块 B，各自汇报，互不干扰。解决的是：能不能并行推进。

Workflow——流水线。把这些串起来，从输入到输出，能被重复执行。解决的是：这件事能不能自动化。

这四个东西分清楚，脑子会清爽很多。

以前我全混在一起，结果什么都理解了一半，什么都做不利索。

---

<!-- Step 3: 并行开发 -->

然后我试了一次，真正让我有点震撼的——并行开发。

第一次用 Git Worktree 配合多个 Agent 的时候，我坐在那发了一会儿呆。

写一个小 Spec，把任务拆成三块。

一个 Agent 去查现状，一个去改前端，一个去补测试。

每个人在自己的 Worktree 里干活，互不干扰，最后我统一 Review。

那个感觉很奇怪——

好像你不是在写代码，你是在带一个组。

当然，翻车的时候也很壮观。

有一次 Spec 没拆清楚，三个 Agent 就像三个很努力但方向不一样的实习生。

一个在改命名，一个在改架构，一个顺手格式化了五百个文件。

我打开 Git Diff 的那一刻，完全不知道从哪里看起。

---

<!-- Step 4: Agent Engineering 本质 -->

所以我后来对「Agent Engineering」的理解，不一样了。

它不是学几个新词。

不是把工具栏装满。

它更像是——你终于开始把 AI 当成一个真正会消耗资源、会偏航、会互相干扰的工程系统来管理。

上下文要管。

能力边界要管。

分工要管。

交接要管。

你开始像项目经理一样思考，也开始像 Tech Lead 一样收口。

写代码，反而只是最后一步。

---

<!-- Ch06 · 工程兜底 -->
<!-- Step 1: Git 重要性 -->

能力越大，越需要安全网。

最后这部分，我想讲，怎么让整个项目别被带沟里。

有一次 Agent 在改一个功能，越改越顺，它自己说没问题，日志看起来也正常。

我一开心，准备收工。

结果第二天一跑，核心流程挂了。

而且挂得特别安静——

页面能开，接口也有返回，但业务已经悄悄歪掉了。

整整一个下午，我才找到问题在哪里。

从那以后，我重新认真学了一遍 Git。

小步提交，一个功能一个 Commit，开实验先建分支，大改之前先留退路。

Agent 一旦开始连续改很多文件，你必须让自己随时能停、能看、能退。

不然等它一口气吐出几千行 diff——

你不是在 Review，你是在哭着考古。

可以不迷信模型，但一定要迷信版本控制。

---

<!-- Step 2: CI + Hooks -->

还有 CI 和 Hooks。

我以前对 CI 的感觉，特别像交作业。

提交上去，等它判卷，红了就改，绿了就收摊。

后来和 Agent 一起工作多了，我才发现 CI 真不是装饰品。

它是那个不会跟你客气的机器审查官。

你觉得没问题，它说：不，你有问题。

而且它不会被你的自信打动。

这一点太重要了——

人和 Agent 一起干活的时候，特别容易进入一种幻觉：

进展好快，终端没报错，所以大概没事。

但工程世界最怕「大概」。

Hooks 也一样。

就是你在流程里提前埋的绊马索，在错误动作发生之前，先把你拦一下。

这些东西平时看起来很烦。

真出事的时候，你会感谢当时那个嫌麻烦但还是写进去的自己。

---

<!-- Step 3: 测试是最后防线 -->

最后是测试。

我以前最喜欢省的就是这个。

心想：差不多，跑起来没报错，应该没问题。

但 Agent 最危险的地方，不是它不会写。

是它会写出那种——看起来很对，运行也像对，但其实不对的代码。

注释写得很认真，结构也挺优雅，逻辑看起来很严密。

你一跑真实场景，啪——没了。

后来我就先把测试意图定下来。

不是让 Agent 先写功能，而是先定好：这几个用例必须过。

这样它就不是在完成一个模糊愿望，而是在满足一个明确边界。

测试不只是为了抓低级 bug。

是为了抓那种「逻辑看起来优雅，但业务已经歪了」的高级翻车。

肉眼最容易心软，测试不会。

---

<!-- Step 4: 总结升华 -->

讲到这里，这半年的变化其实就很清楚了。

半年前，我理解的 Vibe Coding 是什么？

对着 AI 许愿，然后等待奇迹。

现在我理解的 Vibe Coding 是什么？

先想清楚目标，写清楚边界，安排好分工，过程中不断 Review，最后用 Git、CI 和测试把场面兜住。

以前你写错一段代码，最多自己返工。

现在你描述错一次意图，可能是一群 Agent 一起往沟里跑。

我看着那几千行 diff，突然就明白了——

会不会写代码不重要。

会不会想清楚，才是命门。

你不是那个在旁边祈祷 AI 发挥好的人。

你是得想清楚这场仗怎么打的人。

以后别再问：「AI，你能不能帮我写完这个功能？」

换成：「这场仗，我应该怎么带你打？」

这两句话的差距，真的就是这半年的差距。

这里是阿篓，我们下期见。
